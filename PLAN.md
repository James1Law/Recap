# Recap — Plan

**Status:** awaiting approval (M0)
**Author:** Claude (lead engineer) · **Product owner:** James Law
**Date:** 2026-09-03

A chat-first voyage estimator for ship chartering. A charterer types their own shorthand and
gets back a TCE estimate, a full cost breakdown, and the assumptions behind it.

This document is the contract for what we build. Nothing here is code yet.

---

## 1. Scope

### In scope — the four demo scenarios

These are the acceptance criteria. Everything else is secondary.

1. **Cold estimate.** `70k mt iron ore tubarao/qingdao, laycan 15-20 oct, cape`
   → TCE card, cost breakdown, visible assumptions.
2. **What-if.** `what if bunkers are 520?` → recalculates in context, shows the delta.
   Also `actually the rate we're going with is 24.50` → same mechanism.
3. **WhatsApp pull.** `estimate the voyage in my chat with Vlad` → reads a mocked thread,
   states what it inferred, estimates it.
4. **Autocomplete.** Typing `Tub` ghost-completes to `Tubarão` inline, no network call.

### Out of scope for the prototype

Multi-tenancy, auth, real WhatsApp data, persistence beyond the browser session,
port-cost currency conversion, ECA/MGO zone modelling, laytime/demurrage *calculation*
(see §5.6 for what we do instead), weather routing, real market data feeds.

## 2. Non-negotiable architecture rule

**The LLM never does arithmetic.**

The model has exactly one job: turn messy natural language into a validated parameters object.
Every number on screen comes from a pure TypeScript function.

```
user shorthand
      │
      ▼
[ LLM ]  extracts params only ─────────► VoyageParams (Zod-validated, loose, nullable)
      │
      ▼
[ resolve.ts ]  deterministic lookups ─► VoyageInput (fully specified, every field set)
      │         ports, vessels, cargoes, distances,          + Assumption[]  ← provenance
      │         bunker prices, market rate, defaults
      ▼
[ calculate.ts ]  PURE. no I/O. no lookups. no defaults. ─► VoyageEstimate
      │
      ▼
[ EstimateCard ]  renders breakdown + assumptions + warnings
```

### Why the resolver is a separate layer

This is the most important structural decision in the plan, so it is worth being explicit.

`calculate.ts` has **no default values at all**. It cannot invent a number, because it is
handed a `VoyageInput` in which every field is already populated. Every default, every
fixture lookup, every "we assumed a standard Capesize" lives in `resolve.ts`, and each one
emits an `Assumption` record as it happens.

That gives us the answer to the conference question — *"where did that 18,400 come from?"*
Tap the number → see the line item → see which assumption fed it → see whether that value
came from **you**, from a **fixture**, or from a **system default**:

```ts
type Assumption = {
  id: string;            // 'bunker.vlsfo.price'
  label: string;         // 'VLSFO price, Singapore'
  value: string;         // '565.00 USD/mt'
  source: 'user' | 'fixture' | 'default';
  note?: string;         // 'you said 520 — overriding fixture 565'
  verified: boolean;     // false = TODO: verify with James
};
```

If a chartering manager challenges a figure, we can show them the chain in two taps.
That traceability is the product, not a nicety.

### Units: branded types

The brief asked that a unit mix-up be *a compile error, not a wrong number in front of a
customer*. Field naming alone (`distanceNm`) reads well but compiles happily when you pass
knots into a nautical-miles slot. So:

```ts
type Nm = number & { readonly __unit: 'nm' };
type Knots = number & { readonly __unit: 'kn' };
type MtPerDay = number & { readonly __unit: 'mt/day' };
type Usd = number & { readonly __unit: 'usd' };
```

Branded at the **boundaries** (fixture types, `VoyageInput`, `VoyageEstimate`) and unwrapped
once on entry to the calculator, so the arithmetic inside stays readable. This is a judgement
call with a little ceremony attached — say the word and I will drop to naming conventions only.

## 5. The calculator

`lib/estimate/calculate.ts`. Pure function, no I/O, no randomness, no clock.

```
TCE = (gross freight − voyage costs) / voyage days
```

### 5.1 Voyage days

```
ballast steaming = ballastDistanceNm / (ballastSpeedKn × 24)     [0 by default — §5.2]
laden steaming   = ladenDistanceNm   / (ladenSpeedKn   × 24)
port days        = qty/loadRateMtPerDay + qty/dischRateMtPerDay + turnTime per port
weather margin   = steaming days × marginPct
```

### 5.2 Ballast leg — default is none

Confirmed: a cold estimate assumes **APS at the load port, zero ballast leg**, stated loudly
as an assumption. Adding `open qingdao 10 oct` to the shorthand introduces a real ballast leg
from that position. This is also what the ballast-heavy golden test exercises.

### 5.3 Voyage costs

Bunkers at sea (VLSFO, laden and ballast legs separately) · bunkers in port (MGO, idle and
working) · port disbursements per call · canal dues where the routing uses one ·
address commission · brokerage.

### 5.4 Freight rate — both directions

Confirmed: Recap **assumes a market rate** for the lane when you do not give one, labels it
`assumed market rate` in the assumptions block, and corrects itself when you say
*"actually the rate we're going with is X"* in the next message.

Two exported functions:

```ts
calculateVoyage(input: VoyageInput): VoyageEstimate            // rate → TCE
solveFreightRate(input, targetTceUsdPerDay): FreightSolution   // TCE → rate
```

The inverse is a closed form, not a search. Since commission is the only cost that scales
with freight:

```
TCE·D = F·Q·(1 − c) − C_other      ⇒      F = (TCE·D + C_other) / (Q·(1 − c))
```

Exact, instant, and it gives us a free property test: `solveFreightRate` at a target,
fed back through `calculateVoyage`, must return that same target TCE to the cent.

### 5.5 Commissions

Confirmed defaults, applied unless the prompt says otherwise: **3.75% address commission +
1.25% brokerage**, both on gross freight, both shown as separate line items. The parser picks
up explicit mentions (`2.5% addcomm`, `1.25 bkge`) and overrides.

### 5.6 Port time and demurrage

Confirmed approach: seed realistic-looking turn-time and load/discharge figures as fixture
data, clearly labelled, and treat demurrage as **conditional** — if the user supplies a
demurrage rate, we show an indicative exposure alongside the estimate; if they do not, we
say nothing rather than guess. We do not model laytime terms (SHINC/SHEX/WWD) in v1.

### 5.7 Bunkers and weather

Confirmed: VLSFO at sea, MGO in port, priced from fixture hub prices. **No ECA modelling** —
the demo lanes do not touch one, and grade-splitting adds real complexity for no demo value.
Weather margin **5%** on steaming days.

### 5.8 Output

```ts
type VoyageEstimate = {
  tceUsdPerDay: Usd;
  grossFreightUsd: Usd;
  voyageDays: { ballast; laden; port; weatherMargin; total };
  lineItems: LineItem[];      // every cost, with the assumption ids that fed it
  assumptions: Assumption[];  // §2 — provenance on every one
  warnings: Warning[];        // 'no ballast leg assumed', 'distance unverified'
};
```

The card renders all three lists. Warnings are not hidden behind a disclosure.

### 5.9 Golden tests — and the review gate

Three cases: **Cape iron ore** (Tubarão→Qingdao), **Panamax grain** (US Gulf→Japan),
**ballast-heavy edge case** (long ballast, short laden).

Per the brief, I will write out the inputs and outputs of each in plain English and **stop
for your sign-off before they become fixtures**. Until you have signed them off they are my
guesses, and a golden test built on a guess is worse than no test — it locks the wrong number
in and calls it correct.

## 6. Chat, tools, and the what-if flow

One route, `app/api/chat/route.ts`. `streamText` with a system prompt assembled from
`glossary.ts` plus the fixture catalogue, and three tools:

| Tool | Job |
|---|---|
| `estimateVoyage` | fresh estimate from extracted params |
| `reviseEstimate` | apply overrides to the previous estimate |
| `readConversation` | pull a (mocked) WhatsApp thread |

### What-if is stateless

`reviseEstimate` takes only `{ overrides }`. The route finds the most recent
`tool-estimateVoyage` / `tool-reviseEstimate` output part **in the incoming message history**,
re-validates it with Zod, applies the overrides to its stored `VoyageInput`, and recalculates.

No server session store. The provenance lives in the transcript, it works identically in
offline mode, and it is trivially unit-testable. `what if bunkers are 520?` becomes
`{ overrides: { bunkerVlsfoUsdPerMt: 520 } }` and the card renders both estimates with the
changed lines highlighted.

### Graceful failure

If extraction fails, we return what we *did* understand and ask **one** specific question
("I got 70,000 mt iron ore Tubarão→Qingdao — which size vessel?"). Never a blank screen,
never a stack trace.

## 7. Autocomplete

Confirmed: inline ghost text, custom-built. AI Elements ships `PromptInputCommand*`, which is
an `@`-mention dropdown — not what you asked for, and a dropdown reads like every other search
box. So this is ours to write.

- Index built at module load from fixtures: ports, vessels, cargoes, glossary terms.
  Roughly 150–200 entries — a sorted array with a prefix scan, not a trie. Boring is correct.
- Accent- and case-insensitive: NFD normalise, strip diacritics, so `Tub` → `Tubarão`
  and `tubarao` matches too.
- Completes the current word only. **Tab** or **→** accepts, **Esc** dismisses.
- Rendered as a mirrored overlay div behind the textarea with identical typography, so it
  survives line wrapping.
- **Zero network calls.** Conference wifi is assumed to be terrible.

## 8. WhatsApp

```ts
interface ConversationSource {
  listThreads(): Promise<Thread[]>;
  getMessages(threadId: string): Promise<Message[]>;
  findThreadByContact(name: string): Promise<Thread | null>;
}
```

Three methods, not the two in the brief. I fetched the real
[whatsapp-mcp](https://github.com/lharries/whatsapp-mcp) tool surface and it exposes
`list_chats`, `list_messages`, `get_direct_chat_by_contact`, `search_contacts`. Demo scenario 3
is *"my chat with Vlad"* — a contact lookup, not a thread id — and that maps 1:1 onto
`get_direct_chat_by_contact`. Adding the third method now means swapping the real client in
later is a config change, as intended.

- `MockWhatsAppSource` — reads `fixtures/threads/*.json`. This is what we demo.
- `WhatsAppMcpSource` — real MCP client, every method throwing `NotImplementedError`,
  behind `ENABLE_WHATSAPP_MCP` (default off).

Three threads in genuine broker shorthand — mid-negotiation, no punctuation, abbreviations.
Every mocked thread carries a **DEMO DATA** badge in the UI. We are never showing a real
person's messages on a conference screen.

## 9. Demo resilience — `DEMO_MODE=offline`

Offline mode fakes **only the LLM's extraction step**. The numbers are still computed by the
real `calculate.ts`.

That distinction matters three ways: the figures on screen are defensible even with the wifi
off; offline mode exercises the same code path as live, so it is a real test rather than a
stunt; and it means **M1 through M4 need no API key at all** — which is just as well, because
we do not have one yet.

`lib/demo/offline-director.ts` matches the user's message against the four scenarios and emits
a genuine UI message stream with tool-call and tool-result parts. Playwright runs against it,
so **CI needs no secrets**.

Plus: a reset button, and phone-width usable throughout — that is the actual story we are telling.

**R1 — The domain numbers are mine, not yours. This is the big one.**
You have signed off commissions (3.75/1.25), the weather margin (5%), no ECA, and no ballast
by default. You have **not** given me: nautical-mile distances, vessel speeds and consumptions,
port disbursements, load/discharge rates, turn times, bunker hub prices, or lane market rates.

presented as fact until you have corrected it. **An unverified number that looks confident is
the single thing most likely to kill this demo**, so the M2 gate is not a formality.

**R2 — I could not read the AI SDK prose docs.**
This sandbox's egress proxy blocks `elements.ai-sdk.dev` and `ai-sdk.dev`. Component names
come from the vendored skill (129 reference files, revision-locked in `skills-lock.json`) and
versions from the npm registry, so those are solid. But three API surfaces are **provisional**
until you unblock those domains: multi-step tool calling (`stopWhen` / step count), the
UI-message-stream constructors offline mode needs, and the exact `streamText` tool option
names in v7. All three are M3 concerns. **Verification debt is logged in §13.**

**R3 — No API key yet.** Mitigated by the offline-first sequencing above. M6 is the only
milestone that blocks on it.

**R4 — Ghost text vs `PromptInputTextarea`.** The AI Elements textarea may control its own
value or not forward a ref, which would break the overlay. Fallback: our own textarea styled
to match. Costs a day at worst, and we find out at M4.

**R5 — Next 16 is new.** shadcn/ui and the AI Elements CLI may lag it. If the CLI misbehaves
at M1 we drop to the latest Next 15 — a config change, caught immediately.

**R6 — Extraction reliability on broker shorthand.** `1/1/1`, `dop`, `wog`, `abt` are not in
general web text in chartering senses. Mitigated by the glossary in the system prompt, strict
Zod, and the clarify-one-question failure path. Genuinely needs real-input testing at M3.

**R7 — Class → vessel resolution.** You liked both a representative ship and a class average.
Defaulting to a **named representative vessel** per class, because it is traceable — the card
can say *"assumed MV Iron Trader, 180,000 dwt"* and you can defend it. A class average is
harder to challenge but also harder to explain, and is impossible to point at. The averaging
function ships alongside as an alternative resolution mode. Overrule me if you would rather
average by default.

**R8 — No `main` branch.** The repo was created empty, so my branch is its only branch and
GitHub will not open a PR with no base to merge into. One-line fix, needs your permission —
see the note at the end of my last message.
